## Working in this repo

### Commands

- `npm test`: run the vitest suite (`tests/federation.test.ts`).
- `npm run dev`: build the UI and Electron code, then launch the app.
- `npm run build:electron`: compile `electron/` to `dist-electron/` (needed before `npm run mcp` or after pulling changes).
- `npm run mcp`: start the stdio MCP server.

### SQLite

- Storage uses Node's built-in `node:sqlite` only (`openSqliteAdapter` in `electron/db/database.ts`); there are no native modules to compile.
- The app runs on Electron 45 (bundled Node 24); tests and the stdio MCP CLI need Node 22.13+ (enforced by `engines` + `.npmrc` `engine-strict`).
- Electron 45 deprecates the synchronous `safeStorage` methods used by `electron/security/keyVault.ts`; they're removed in Electron 46, so moving to Electron 46+ requires switching key access to the async API.

### Layout

- `electron/main.ts`, `electron/preload.ts`: IPC handlers and the renderer API.
- `electron/db/database.ts`: SQLite schema, queries and the signed site bundle. Editing an item (`updateItem`) keeps its id, canonical URL, type and `createdAt` (friends' endorsements point at the canonical URL) and sets the optional `updatedAt`, which the page shows as "edited". Wall post bodies (`type: 'post'`) are Markdown, rendered with `renderMarkdown`; other items' commentary stays plain text. Derived titles and snippets use `markdownToPlainText`.
- `electron/services/`: ring crawler (friends), ring service (webrings: hubs, join requests, sync), static site generator, publisher, persona manager.
- `electron/mcp/`: MCP server (stdio CLI and loopback HTTP/SSE).
- `electron/security/`: private key encryption at rest.
- `src/shared/schema.ts`: zod schemas, signing and verification, did:web.
- `src/studio/App.tsx`: studio UI.
- `src/studio/SiteDesignPanel.tsx`: Site Design (look & feel, page layout blocks). The published page and Studio's preview both come from `siteGenerator.buildStandaloneProfileHtml` (preview mode adds a media `<base>` and a link bridge); there is no second renderer.
- `electron/services/siteTemplates.ts`: the page templates. Each theme maps to an arrangement (`stack` for the classic themes; `sidebar`, `deck`, `rails`, `grid` and `reel` for Facepace, Tweetdeck, XtraSpecial, Instapick and Tik Talk), with its CSS. `renderTemplatePage` is self-contained like the Markdown renderer, because the generator embeds its source in the published page. A profile with an unknown theme falls back to `neo-webring` instead of failing to parse.
- `electron/services/pageEnhancements.ts`: the published page's interactive extras: photo lightbox, post view (`#post-<id>`, `#photo-<id>`) and sortable tables, using the native `<dialog>`. It's self-contained and embedded the same way; it's left out when `appearance.interactions` is `off`. It also puts a short hand-off sheet before every `webring://` link: Open in Webring Studio, a copyable page link for visitors without the app, and a per-site "don't ask again" (`localStorage`). The browser's own protocol prompt can't be customised.
- History window: published `items.json` holds the last 90 days (at least 50 items) and lists older items in `archive: { since, months: [{ month, url, count }] }`; each `api/archive/items-YYYY-MM.json` is a signed `ItemsDocument`, signed with a fixed time (`signDocument(..., created)`) so unchanged months are byte-identical. Readers must only prune a friend's feed rows and endorsements created at or after `archive.since`. Studio's own data uses the full bundle; `buildSignedSiteBundle({ publish: true })` is what gets published, previewed and fingerprinted. The feed window (`local_settings.feedRetentionDays`, default 90, 0 = forever) limits `network_feed` but never endorsements or saved posts. `fetch_cache` holds ETag / Last-Modified for friends' files, kept only for verified documents. Saved posts (`saved_posts`, images in `media/saved/`) are private: never exported or published (`getLocalMediaReferences` excludes them; clean-up keeps them via `getSavedMediaReferences`).
- `src/shared/markdown.ts`: safe Markdown renderer for text blocks; it's self-contained because the generator embeds its source in the published page.
- `tests/federation.test.ts`: test suite.
- `images/logo-icon.png`: the source logo. `scripts/generate-icons.py` (macOS) derives everything else from it: `build/icon.icns|ico|png` and `build/icons/` for packagers, `electron/assets/` (window, dev dock and tray icons, including the monochrome macOS menu-bar template) and `public/favicon.png` / `public/logo-mark.png` for the Studio window. Edit the logo, then rerun the script; don't hand-edit the generated files. On macOS, `scripts/brand-dev-electron.mjs` renames Electron's dev bundle to "Webring Studio" (Dock tooltip, app menu, Cmd+Tab) and gives it the icon. Never set `productName` or call `app.setName()` to change the displayed name: both change the data folder (`webring-studio`) and would hide existing personas.
- `docs/architecture/federation.md`: federation design and boundaries.

### Conventions

- The zod schemas in `src/shared/schema.ts` are the data contract.
- Everything published goes through `buildSignedSiteBundle()`.
- Peer data is read only through the curated view (`getCuratedNetworkFeed` / `getCuratedEndorsements`), never the raw tables.
- Network fetches of peer or hub URLs go through `defaultJsonFetcher` in `electron/services/ringCrawler.ts`, which blocks private and local addresses (`electron/security/networkGuard.ts`). Don't call `fetch` directly for peer data. Set `WEBRING_ALLOW_PRIVATE_PEERS=1` to crawl LAN or localhost peers during development.
- Media Library (`electron/services/mediaLibrary.ts`, `imagePipeline.ts`): local photos are re-encoded (≤ 2048 px web copy, ≤ 480 px thumbnail, EXIF/GPS stripped) and stored content-addressed under the persona's media folder; originals are kept locally and never published. The generator publishes only library files something references (`db.getLocalMediaReferences()`: photos, post images, album covers, profile images), plus a signed manifest per album (`buildSignedAlbumManifests`). Never copy the whole media folder. Uploaded profile photos and banners live in `profile/<avatar|banner>-<hash>.<ext>` (`setProfileImageFromFile`); there's one of each, and the library clean-up deletes a replaced one.
- Publishing is incremental (`electron/services/publishSync.ts`): each destination has a ledger (`publish_ledger`). Only changed files are uploaded, media before pages, and only files Studio published there (or anything under `media/albums/`) are deleted. Keep new publish targets on `planSync` / `applySyncPlan`.
- Secrets are sealed with `electron/security/keyVault.ts` (OS keychain): the private key and the publishing credentials (`password`, `githubToken`). `getProfile()` returns `STORED_SECRET_PLACEHOLDER` for credentials; sending the placeholder back keeps the stored value. Only the publish path decrypts them (`db.withStoredCredentials` / `getPublishCredentials`), right before connecting. Never put real credentials in renderer state, MCP results or logs.
- Sync All and publishing are shared by the buttons, MCP tools and the scheduler through `runSyncAll` / `publishTo` / `runScheduledPublish` in `electron/services/jobs.ts`; don't duplicate them. Scheduled and manual runs for the same persona are serialised with `Scheduler.runExclusive`. Background jobs open their own persona context (`PersonaManager.withPersonaContext`), never the active one. Schedules live in `userData/scheduler.json` (persona ids only) and run in the Electron main process, since signing needs the OS keychain.
- Webring data is fetched through `RingService.fetchPublicJson` (https only, never `file://` or local paths). Ring decisions trust only documents signed by the site's pinned key (`site_keys`); unverified hubs, key changes and failed fetches may warn but never remove a member. See the Webrings section of `docs/architecture/federation.md`.
- Schema changes are additive: `CREATE TABLE IF NOT EXISTS` or a guarded `ALTER TABLE` in `initializeSchema`.
- Any change to federation behaviour gets a test in `tests/federation.test.ts`.
